# Production, релизы и восстановление

Это краткое руководство для технического оператора. Оно не заменяет проверку конкретного сервера перед командой: пути, SHA, владельцы файлов и активные units нужно подтверждать read-only проверкой на VPS.

## Границы системы

- Next.js web-приложение обслуживает четыре HTTPS-домена и запускается отдельным непривилегированным пользователем.
- API Zhangak по эталонной конфигурации слушает только `127.0.0.1:3210`.
- PostgreSQL по эталонной конфигурации слушает только `127.0.0.1:5433`.
- Браузеры ходят только через HTTPS и `/v1`; API и PostgreSQL не должны открываться в интернет.
- Релиз web — immutable standalone-артефакт, названный SHA коммита. Runtime secrets живут вне артефакта.

Точная процедура immutable-релиза, атомарной активации и rollback находится в [deploy/README.md](../../deploy/README.md). Для API отдельно используйте [deploy/api/README.md](../../deploy/api/README.md). Не копируйте незакоммиченный каталог на сервер и не редактируйте `current` напрямую.

## Конфигурация и секреты

Значения ниже не помещают в Git, release artifact, chat, скриншоты или `NEXT_PUBLIC_*`. В production web-runtime используется `/etc/zhangak/zhangak.env`; API-конфигурация хранится отдельным root-owned файлом согласно [API deploy guide](../../deploy/api/README.md).

| Система | Требуемые параметры | Правило |
| --- | --- | --- |
| Web/BFF | `ZHANGAK_API_INTERNAL_URL` | Только loopback URL приватного API. |
| AI, когда функция реально активирована | `AI_PROVIDER` и ключ выбранного поставщика, например `DEEPSEEK_API_KEY` | Только server-side; модель и лимиты описаны в [AI runbook](../ai-provider.md). |
| API | `DATABASE_URL`, `JWT_SECRET`, `ALLOWED_ORIGINS` | Обязательны; API отказывается стартовать без них. `JWT_SECRET` — минимум 32 символа и не шаблон. |
| API runtime | `HOST`, `PORT`, `DATABASE_SSL`, `ACCESS_TOKEN_TTL_SECONDS`, `REFRESH_TOKEN_TTL_DAYS`, `TRUST_PROXY`, `ZHANGAK_API_RELEASE_SHA` | Значения должны соответствовать окружению и HTTPS reverse proxy. |
| Однократный bootstrap | `ZHANGAK_ADMIN_EMAIL`, `ZHANGAK_ADMIN_PASSWORD`, `ZHANGAK_ADMIN_NAME` | Используются только для создания первого super-admin на сервере; не добавляются в постоянный env-файл и не печатаются. |

Шаблоны содержат **имена**, а не реальные секреты: [web env example](../../deploy/zhangak.env.example), [API env example](../../deploy/api/zhangak-api.env.example). `DEEPSEEK_API_KEY`, пароль БД и JWT secret нужно считать скомпрометированными, если они когда-либо попадали в чат, commit, CI log или браузерный bundle: заменить секрет, перезапустить затронутый сервис и отозвать старое значение.

## Перед выпуском

1. Рабочее дерево чистое, SHA зафиксирован.
2. Выполнены обязательные проверки из [основного README](../../README.md), а для API — `npm --prefix backend run check` и `npm --prefix backend test`.
3. Изменение миграции проверено на чистой disposable PostgreSQL дважды; migration ledger согласован. В частности, release настроек профиля требует применения `backend/migrations/004_student_profile_preferences.sql` до включения UI.
4. Релизный артефакт собран и прошёл `npm run smoke:standalone`.
5. Проверены хотя бы один ученический, один административный и один неавторизованный сценарий на staging/контролируемом окружении.
6. Зафиксированы версия, время, ответственный, ожидаемые изменения и rollback SHA.

`npm run lint` обязан завершаться без ошибок; известные предупреждения также
не должны расти без осознанного review. Полная E2E-проверка с disposable
PostgreSQL остаётся отдельным обязательным этапом, а не заменяется unit-тестами.

## После выпуска: внешний и внутренний health-check

Проверьте внешне:

```sh
curl --fail --silent https://zhangak.com/api/health
curl -I https://zhangak.com/
curl -I https://platform.zhangak.com/
curl -I https://offline.zhangak.com/
curl -I https://admin.zhangak.com/
```

Проверьте на сервере, без публикации внутренних портов:

```sh
curl --fail http://127.0.0.1:3210/v1/health
curl --fail http://127.0.0.1:3210/v1/ready
```

Сверьте `releaseSha` health-ответа с SHA активированного артефакта. Затем проверьте, что platform/admin отдают `noindex`, guest не получает данные защищённого API, а student/admin страницы не пересекаются по домену.

Если health-check или ключевой путь не проходит, используйте атомарный rollback из [deploy/README.md](../../deploy/README.md#roll-back-manually). Не «лечите» сбой ручным копированием файлов в `current`.

## Резервные копии и восстановление

Автоматическая копия на втором томе VPS описана в [backup runbook](../../deploy/backup/README.md). Она полезна для восстановления от заполнения системного диска или случайного удаления на основном томе, но **не является off-host резервной копией**: потеря VPS, аккаунта провайдера или шифрования затронет оба тома. Этот runbook — источник точных команд и retention для локальной копии.

Минимальная операционная политика:

1. Делать консистентную резервную копию PostgreSQL по расписанию и хранить её с правами, исключающими обычный web/deploy-процесс.
2. Хранить копии также вне VPS/в независимом хранилище, шифровать их и контролировать доступ.
3. Включать в план все данные, без которых восстановление неполно: PostgreSQL, загружаемые файлы/объектное хранилище при его использовании, конфигурацию инфраструктуры без секретов и зашифрованный реестр секретов.
4. Определить retention, владельца, оповещение о неуспешном backup и допустимые RPO/RTO до приема реальных учебных данных.
5. Минимум раз в квартал выполнять восстановление последней копии в изолированную базу, запускать readiness/checks и фиксировать время/результат. Никогда не проверять restore поверх production.

Исторический [Supabase recovery guide](../database/recovery.md) относится только к архивному источнику. Он не является инструкцией restore собственной PostgreSQL Zhangak и не разрешает вернуть Supabase в production.

## Наблюдение и инциденты

Каждый день оператор проверяет:

- доступность четырёх доменов и срок TLS;
- `systemctl`/journal web и API без повторяющихся restarts;
- свободное место на системном и backup-томе;
- статус последней копии и предупреждений;
- отсутствие публичного доступа к API/PostgreSQL/служебным портам.

Каждую неделю проверяет:

- версию активного SHA;
- обновления безопасности ОС и зависимости по утверждённому окну;
- firewall: наружу нужны только необходимые TLS/SSH порты, а не `3210`/`5433`;
- полномочия пользователей: `deploy` не должен иметь `NOPASSWD: ALL`; нужен только узкий sudo для проверенной активации.

При инциденте:

1. Зафиксируйте время, затронутый домен/сервис, SHA и симптомы без записи секретов/персональных данных.
2. Ограничьте дальнейший ущерб: заблокируйте скомпрометированный аккаунт или отключите затронутую функцию, не удаляя доказательства.
3. Проверьте health, logs, последние релизы и резервные копии в read-only режиме.
4. Выполните rollback или restore только по подтверждённой процедуре.
5. После восстановления смените затронутые секреты/пароли, протестируйте внешний путь и оформите короткий postmortem.

## Нельзя делать

- Не выполнять `git reset --hard`, `rm -rf`, `docker system prune` или миграции без проверенного целевого пути и backup.
- Не открывать PostgreSQL/API в интернет «для удобства».
- Не запускать `supabase db push`, `supabase db reset --linked` и не возвращать SDK Supabase в текущий data plane.
- Не предоставлять `deploy` или приложению полный root-доступ.
- Не печатать, не логировать и не копировать секреты при диагностике.
