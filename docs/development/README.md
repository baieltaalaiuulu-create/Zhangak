# Руководство разработчика Zhangak

Документ объясняет, как безопасно начать работу, где искать код и какой путь
должно пройти изменение до production. Версия runtime закреплена в
`.node-version`; production всегда соответствует конкретному Git SHA.

## Быстрый старт

Требования: Node.js `22.22.2`, npm из `packageManager`, PostgreSQL 16 для
интеграционных проверок backend.

```bash
npm ci
npm --prefix backend ci
npm run dev
```

Web по умолчанию открывается на `http://localhost:3000`. Для полного локального
цикла нужен собственный API на `127.0.0.1:3210` и PostgreSQL. Создайте локальные
env-файлы по шаблонам; реальные production-значения не копируйте.

## Структура репозитория

| Путь | Ответственность |
| --- | --- |
| `app/` | Next.js App Router: страницы, BFF `/v1`, health |
| `components/` | UI-компоненты по доменам и ролям |
| `lib/` | Browser/server клиенты, строгие DTO и чистые вычисления |
| `backend/src/` | Собственный HTTP API, auth, RBAC, PostgreSQL и AI gateway |
| `backend/migrations/` | Последовательные immutable SQL-миграции |
| `backend/test/` | Контрактные и security-тесты API/схемы |
| `tests/` | Web-контракты, DTO, host-routing и пользовательские инварианты |
| `scripts/` | Статические quality/security/data-plane проверки |
| `mobile/` | Отдельный Expo-клиент с bearer-сессией собственного API |
| `docs/` | Продуктовые, учебные, операционные и технические инструкции |
| `deploy/` | systemd, Nginx, backup и атомарная активация релизов |

Generated `node_modules`, `.next`, `backend/dist` и release-архивы не являются
исходным кодом. Не редактируйте их вручную и не используйте как источник
контракта.

## Локальный поток запроса

1. Страница вызывает только same-origin `/v1/platform/*`, `/v1/admin/*` или
   узкий публичный `/v1/public/*`.
2. Next BFF пересылает HttpOnly cookie/разрешённый заголовок приватному API.
3. API заново проверяет сессию, текущую роль и доступ к конкретному объекту.
4. PostgreSQL выполняет параметризованный запрос или транзакцию.
5. API возвращает минимальный DTO; браузер не получает ключи ответов,
   password hash, токены других пользователей или внутренний audit metadata.

Подробная схема находится в [архитектуре](architecture.md).

## Как добавить функцию

### 1. Зафиксировать контракт

- определить роль, домен и владельца данных;
- описать вход, выход, лимиты, ошибки и audit-событие;
- решить, нужна ли миграция;
- запретить клиенту присылать вычисляемые сервером поля (балл, XP, роль,
  student ID текущего пользователя, timestamps).

### 2. Изменить базу

Создайте следующий файл `backend/migrations/NNN_name.sql`. Старые применённые
миграции не редактируются. Добавьте ограничения, индексы, FK и idempotency
ключи на уровне БД. Обновите `backend/scripts/verify-migrations.js` и тест
контракта миграции.

### 3. Добавить backend

- маршрут регистрируется в `backend/src/server.js`;
- тело разбирается с byte-limit и точным списком полей;
- `requireAuth` и capability/RBAC выполняются до чтения данных;
- запросы scoped по authenticated user/assigned group/course;
- связанные записи меняются одной транзакцией;
- внутренние ошибки не возвращаются клиенту;
- привилегированная запись оставляет минимальный `audit_log`.

### 4. Добавить web/mobile клиент

Клиент принимает `unknown`, валидирует DTO и только затем рендерит. Browser web
использует `zhangakApiRequest`; native-клиент — bearer/refresh слой. Не добавляйте
Supabase SDK, прямой vendor AI вызов или production secret в `NEXT_PUBLIC_*`.

### 5. Обновить интерфейс и документацию

Проверьте mobile 390 px, desktop, клавиатуру, focus, пустое состояние, loading,
401/403/404/409/429/503 и повтор запроса. Обновите руководство аудитории и
карту данных. Недоступная функция получает честное состояние, а не фиктивные
цифры.

## Обязательные проверки

Минимум перед commit:

```bash
npm run typecheck
npm run lint
npm run test:unit
npm run check:security
npm run check:own-backend
npm --prefix backend run check
npm --prefix backend test
git diff --check
```

Для изменения маршрутов дополнительно запускайте подходящие `check:*` из
`package.json`. Для миграций CI поднимает disposable PostgreSQL и применяет
весь ledger дважды. Для release обязателен `npm run build` и standalone smoke.

## Git и review

- одна логическая задача — один проверяемый commit/PR;
- не смешивать форматирование всего проекта с функциональной правкой;
- не перезаписывать пользовательские изменения в dirty worktree;
- в PR указать миграции, роли, новые env, тесты, rollback и документацию;
- deployment выполняется только из чистого SHA после зелёного CI.

## Секреты и персональные данные

В Git запрещены: `.env`, API keys, JWT secret, DB URL с паролем, session token,
экспорты учеников, резервные копии и реальные ответы/документы. Если секрет
появился в чате или commit, его нужно считать раскрытым и заменить.

## Диагностика

| Симптом | Проверка |
| --- | --- |
| Login переключает страницы | домен роли, cookie текущего origin, `/v1/auth/me`, роль/тип пользователя |
| 401 | сессия отсутствует/отозвана/истекла; не обходить auth в UI |
| 403 | роль, active enrollment, назначение группы, Origin |
| 409 | бизнес-инвариант: переход статуса, одна запись на курс, повторная попытка |
| 503 | API/DB/AI feature flag или внешний провайдер; проверить readiness и journal |
| Миграция не стартует | checksum ledger, порядок номеров, чистая PostgreSQL, точный env |

Production-команды, rollback и backup находятся только в
[операционном руководстве](../operations/production.md).
